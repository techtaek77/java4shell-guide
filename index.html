🚨 CVE-2026-114938 · CVSS 9.2 (Critical) ☕ OpenJDK / Java4Shell 🦖 벨로키의 3분 해부

“= 하나 때문에 Java가 남의 집을 64바이트씩 도배한 사건”

GeekNews #37370에 올라온 Java4Shell 취약점, 대체 왜 생겼고 왜 하필 최신 x86-64 서버에서만 터지는지 쉽게 풀어봅니다.

한 줄 요약부터 보고 가자

Java가 Base64 문자열을 초고속(AVX-512)으로 디코딩하다가, 끝에 붙은 이상한 패딩(=)을 보고 출력 길이를 음수(예: -2)로 잘못 계산했습니다.

문제는 이 음수 길이를 CPU 비트마스크 명령어에 그대로 넘기면서 벌어집니다. “2바이트만 써!”라고 해야 할 걸 “64바이트 풀로 다 덮어써!”로 알아들어, 내 배열을 뚫고 옆집 Java 객체 메모리(Heap)까지 최대 62바이트를 덮어쓰게 된 겁니다.

💡 핵심: Java 코드의 잘못이 아니라, 속도를 높이려고 JVM 내부에 직접 짠 어셈블리 최적화(Intrinsic)의 계산 실수입니다!
벨로키: “분명 디코딩만 시켰는데 왜 옆집 메모리까지 넘치지…?”

1Base64와 패딩(=)이 뭔데?

Base64는 이진 데이터(이미지, 토큰 등)를 알파벳·숫자로 바꾸는 방식입니다. 원본 데이터 3바이트를 글자 4개로 묶어서 표현합니다.

🥚 계란판 비유
4칸짜리 계란판에 데이터를 담는데, 마지막에 계란이 1~2개 모자라면 빈칸을 스티로폼(=)으로 채웁니다.
그래서 정상 Base64 끝에는 =가 0개, 1개, 또는 최대 2개까지만 붙을 수 있어요.

그런데 누군가 악의적으로 64글자(또는 128글자) 뒤에 이상한 위치의 =를 슬쩍 끼워 넣으면 어떻게 될까요? 원래라면 “어, 문법 틀렸네!” 하고 에러(`IllegalArgumentException`)를 내고 멈춰야 정상입니다.

2진짜 범인: 너무 빨라서 앞을 못 본 AVX-512 & 음수 마법

OpenJDK 17.0.6부터는 Base64를 한 글자씩 번역하지 않고, 최신 CPU의 AVX-512 VBMI 기능으로 한 번에 64바이트짜리 대형 트럭으로 밀어버리는 어셈블리 고속도로(StubRoutines)를 씁니다.

트럭이 마지막 찌꺼기 데이터를 처리할 때, 패딩(=) 개수를 빼서 남은 출력 길이를 구합니다. 여기서 이상한 패딩 입력이 들어오면 출력 길이가 0보다 작은 음수(예: -2)로 떨어지는(Underflow) 버그가 터집니다!

“-2바이트만 쓰라고? OK, 64바이트 다 찍어버릴게!” (bzhiq의 배신)

왜 음수가 64바이트 도배가 되나요?

CPU는 “64바이트 중 앞의 N바이트만 써라”는 마스크를 만들 때 bzhiq 같은 비트 명령어를 씁니다.

여기에 음수(-2)가 들어가면 부호 없는 아주 큰 숫자로 해석되면서, “일부만 쓰기” 마스크가 “64바이트 전부 허용” 마스크로 변신해 버립니다!

직후에 Java가 “어, Base64 문법 틀렸네!” 하고 예외를 던지긴 하는데… 이미 옆집 힙 메모리 62바이트를 덮어쓴 뒤입니다. (이게 심하면 원격 코드 실행 RCE로 이어집니다.)

🎮 직접 눌러보는 Heap 침범 시뮬레이터
계산된 출력 길이
+3 bytes
bzhiq 쓰기 마스크
하위 3칸만 ON
Heap 메모리 상태
안전 (경계 준수)
메모리 칸 (초록 = 내 2~3B 버퍼 / 회색 = 옆집 Java 객체 / 빨강 = 64B 덮어쓰기 침범!)
정상 입력입니다. 필요한 3칸만 깔끔하게 쓰고 옆집 메모리는 건드리지 않았습니다.

3어떻게 들어와서, 옆집 객체의 뭘 조작할까?

“어차피 이상한 Base64 넣으면 서버가 400 Bad Request 내고 끝나는 거 아닌가?” 싶지만, 예외(IllegalArgumentException)를 던지기 직전 어셈블리 단계에서 이미 64바이트를 써버린다는 게 함정입니다. try-catch로 감싸도 메모리 손상은 이미 일어난 뒤입니다.

1) 어디로 들어오나? (로그인 없이도 닿는 입구들)

🔑 HTTP 인증 헤더 · JWT

Authorization: Basic ... 헤더나 Bearer <JWT> 토큰은 로그인 검증을 통과하기 전에 서버가 먼저 Base64 디코딩을 돌립니다. 인증 없는 공격이 가능한 이유입니다.

📦 API JSON · 웹훅 · 첨부 데이터

이미지/파일을 Base64 문자열로 받는 API, 서명 검증용 웹훅 페이로드 등 Base64.getDecoder().decode()를 한 번이라도 타는 모든 입력이 통로가 됩니다.

2) 옆집 객체의 뭘 덮어써서 사고를 내나?

Java의 모든 객체는 힙(Heap) 메모리에 나란히 붙어 있습니다. 공격자가 요청을 여러 번 보내 내 작은 배열 바로 옆에 원하는 타깃 객체가 놓이게 유도(Heap Grooming)한 뒤 62바이트를 덮어쓰면, 아래 3가지 단계로 사고가 커집니다.

🎯 옆집 메모리를 덮어쓰면 실제로 무슨 일이 벌어질까? (클릭해서 확인)
“옆집 객체의 이름표를 찢어버려서 서버가 그대로 멈춤”
Java 객체 맨 앞에는 “내가 누구인지” 적힌 이름표(헤더)가 붙어 있습니다. 여기에 엉뚱한 글자가 덮어써지면, 잠시 뒤 서버가 그 객체를 쓰려다 “이게 도대체 뭐야?” 하고 Java 서버 전체가 뻗어버립니다(장애/먹통).

4우리 서버도 위험할까? (3초 자가진단 & 처방)

다행히 두 가지 조건이 동시에 맞아야 터집니다. 하나라도 해당 안 되면 안전합니다!

🚨 영향 받는 환경

  • OpenJDK / Oracle JDK 17.0.6 이상 (17, 21, 25, 27 포함)
  • x86-64 CPU + AVX-512 VBMI 지원
    (Intel Ice Lake 이상, AMD Zen 4 이상 클라우드 서버 등)
  • 외부 입력을 Base64.getDecoder().decode()로 받는 서비스 (JWT, API 페이로드, 웹훅 등)

🛡️ 영향 없는 환경

  • ARM64 서버 (AWS Graviton, Apple Silicon M시리즈 등)
  • 구형 x86 CPU (AVX-512 VBMI 미지원)
  • Java 8 / Java 11 (이 AVX-512 경로가 아예 없음)

어떻게 막나요?

1순위 (정식 해결): 보안 패치가 적용된 최신 JDK로 업데이트하세요.
(예: 17.0.21.1, 21.0.13.1, 25.0.5.1, 27.0.1.1 이상)

2순위 (당장 재배포/패치 못 할 때 임시 스위치):
JVM 실행 옵션에 아래 플래그 하나만 추가하면 문제의 AVX-512 고속도로를 끕니다.

-XX:-UseBASE64Intrinsics
